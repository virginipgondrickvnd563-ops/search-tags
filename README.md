# Поисковые теги

Проект строит для каждого нормализованного запроса до 10 следующих запросов, которые встречались у не менее пяти разных пользователей в соседних поисках с интервалом не более 30 минут.

## Запуск

В репозитории уже есть датасет `data/logs.parquet`. Из корня проекта выполните:

```sh
docker compose up -d clickhouse
docker compose exec clickhouse clickhouse-client --user app --password app --multiquery --queries-file /docker-entrypoint-initdb.d/01_schema.sql
docker compose exec clickhouse clickhouse-client --user app --password app --multiquery --queries-file /docker-entrypoint-initdb.d/02_load_logs.sql
docker compose exec clickhouse clickhouse-client --user app --password app --multiquery --queries-file /docker-entrypoint-initdb.d/03_build_tags.sql
go test ./...
docker compose up --build web
```

Загрузка из Parquet заменяет полный снимок таблицы логов, поэтому повторный запуск не удваивает строки. Доступные адреса: страница `http://localhost:8080`, API `http://localhost:8080/api/tags?q=платье`.

Параметры сервиса задаются переменными `CLICKHOUSE_ADDR`, `CLICKHOUSE_DATABASE`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `HTTP_ADDR` и `DB_TIMEOUT` (например, `5s`). `DB_TIMEOUT` задаёт таймаут чтения ClickHouse; при его превышении API возвращает JSON и статус 504.

## Схема и расчёт

Логи используют `MergeTree`, месячную партицию по времени и `ORDER BY (user_id, timestamp)`: расчёт оконных соседей группирует события пользователя и сортирует их по времени, а партиции упрощают обслуживание истории. `DateTime64(3, 'UTC')` сохраняет миллисекунды, `UInt64` хранит числовой идентификатор, запрос хранится как `String`. Результат упорядочен по `(query, rank)` для выдачи тегов в нужном порядке.

Нормализация в SQL и Go приводит регистр к нижнему, сворачивает табуляцию, переводы строк, обычный и неразрывный пробел в один пробел и обрезает края. Пустые события сохраняются в последовательности при вычислении соседей, а затем исключаются из пар. Разрыв проверяется сравнением `DateTime64` с `timestamp + INTERVAL 30 MINUTE`, без округления до секунд. При одинаковых метках времени порядок событий не определён; если источник допускает такие события у одного пользователя, для полной воспроизводимости нужен уникальный идентификатор события.

Теги строятся в отдельной staging-таблице и публикуются через `EXCHANGE TABLES`: пока идёт расчёт, API продолжает читать предыдущую завершённую версию. Для этого нужен движок базы данных ClickHouse `Atomic` (он используется для автоматически созданной базы Compose). Порог считается через `uniqExact(user_id)`, то есть уникальные пользователи.

## Проверки

SQL-проверки находятся в `sql/04_checks.sql`: нет self-pairs, число пользователей не ниже пяти, до 10 тегов на запрос и одинаковый результат для `Платье ` и `платье`. Go-тесты проверяют нормализацию (включая NBSP), пустой `q` (JSON 400), параметризованный нормализованный запрос, пустой результат и JSON-ответы 500/504.

## Ежедневное обновление

Для инкрементального пересчёта следует хранить соседние события пользователя на границе загруженного диапазона, дописывать новые события и пересчитывать переходы затронутых пользователей. После обновления агрегатов пар пересчитывается топ-10 только для затронутых запросов, затем новая версия публикуется атомарным обменом таблиц.
